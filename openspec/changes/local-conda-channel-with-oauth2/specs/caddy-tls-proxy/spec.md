# Spec: Caddy TLS Proxy

## Capability

Caddy serves as the TLS-terminating reverse proxy at `repo.thath.local:8443`, enforcing JWT authentication on all conda channel requests via `forward_auth` to the Flask proxy, and serving the channel static files.

## Requirements

### TLS

- Listens on port `8443` (HTTPS)
- Uses certificates generated by `mkcert` at:
  - `certs/repo.thath.local.pem` (certificate)
  - `certs/repo.thath.local-key.pem` (private key)
- `auto_https off` in global options (mkcert manages TLS, not Caddy's ACME)

### Route: `/channel/*`

- Applies `forward_auth` to `http://localhost:5000/auth-check` before serving
- Passes the `Authorization` header to the auth check endpoint
- On `200` from Flask: serves the requested file from the `channel/` directory via `file_server`
- On `401` from Flask: returns `401` to the client, including the `WWW-Authenticate` header set by Flask
- `file_server` root: `./channel` (relative to Caddy working directory, or configurable via env)

### Route: `/oauth/*`

- Unauthenticated — no `forward_auth`
- Reverse-proxied directly to `http://localhost:5000`

### Route: `/.well-known/*`

- Unauthenticated — no `forward_auth`
- Reverse-proxied directly to `http://localhost:5000`

### Logging

- Access log to stdout (default Caddy format is acceptable)

## Constraints

- Caddy must not attempt to obtain ACME certificates (local domain)
- Channel files are served as static files by Caddy — Flask does not serve channel content
- The `forward_auth` check must occur on every `/channel/*` request; no caching of auth results at the Caddy level (short-lived tokens make this important — a cached 200 could outlive token expiry)
- Caddyfile uses relative paths or environment variable substitution where possible to remain portable within the project directory
